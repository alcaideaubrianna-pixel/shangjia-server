# 新推送架构性能与稳定性验证记录

## 范围

仅优化 `unified_stream` 路径。保留旧引擎用于迁移回滚；迁移稳定后再按引用删除旧 dispatcher、旧 recovery 和配置开关。本地测试不得使用真实 Telegram 发送，不得将 Hook 吞吐当作 Telegram 容量。

## 2026-11-10 基线

- 本地 PostgreSQL + Redis DB 15，TG Hook，8 个 publish-worker、1 个 background-worker。
- 1000 份资料，100 个频道，100000 条推送 job；账户使用默认 5 秒发送间隔。
- 连续两个完整分钟成功次数：660、722（所有频道合计）。
- 单频道相邻成功间隔 P50 7.34 秒、P95 11.13 秒；100/100 频道有成功记录。
- PostgreSQL CPU 采样约 5.7 核；连接数 49；advisory lock 等待 0。
- bulk lag 曾超过 17000；不能据此宣称系统已达到稳定容量。
- 这轮是直接注入推送 job 的发送压测，不能证明循环/批次调度覆盖率，也未验证删除队列和优先级。
- 后续观察成功数停在 5000 条手工文本任务；媒体夹具缺少真实路径，出现“媒体文件地址为空”。故上述吞吐只代表文本阶段，不能代表媒体资料吞吐。已补齐媒体路径和 background-worker 的只读测试文件挂载，尚待重跑。

## 本轮修复与证据

1. Stream 同批消息遇到某频道租约竞争后继续处理其他频道；失败消息保持 pending。
2. pending 重试与新消息交替，避免同一忙频道无限阻塞新频道。
3. 有成功进展的批次不因局部竞争强制暂停一秒；全批无进展仍退避。
4. 运行中定期接管其他实例遗留 pending，每轮有界处理；复用批次处理能力。
5. Stream 业务适配器识别数据库已删除任务的旧通知，数据库连接等其他错误仍上抛。
6. Docker 构建缓存 Go module 和编译缓存，避免每次源码修改都重下依赖。

已通过 Stream 测试和相关业务单测；修改后真实服务性能复验仍待完成。新增测试覆盖同批频道隔离、新消息不饥饿、启动后接管。测试通过不等同于全角色运行通过。

## 2026-11-11 账户调度、循环统一与故障验收

本轮保持2个publish-worker，并真实运行web、scheduler、background-worker、media-worker、PG、独立Redis16382/DB15和TG Hook。未部署生产、未调用真实Telegram；本轮使用本地完整资料夹具和已有导入结构，没有重新导入最新生产全量数据。

### 改动

- scheduler只分页读取账户目录；复用background队列，以账户租约和执行预算隔离定时上架、时间循环、批次及恢复。正常全量新引擎不进入旧全局分片扫描或启动全频道重算。
- 资料级循环一轮共用操作号，读取资料与频道后统一准备任务；不再逐频道重复整份资料的准备过程。频道任务、Outbox和run映射在事务内保存，提交后投递通知。
- 删除冗余cycle_engine判断/缓存文件，统一由push_engine接管。时间循环、批次统一生命周期识别；既有会员保护、时钟计算和批次游标复用。
- 手工/编辑不复用其他操作的活动任务；同一操作完整重试不重新打开pending，也不改写已成功记录。
- 手工优先与账户发送间隔分离。真实手工前缀用例曾复现0.19秒间隔，已修复；新引擎读取间隔失败会重试，不直接发送。
- 单频道任务准备使用框架嵌套事务隔离配置错误，失败频道保留failed任务；健康频道继续。资料整体保留失败提示，循环run收口partial/failed，不能把失败留在排队状态或误报全成功。
- 新批次生产复用可扩容background队列，避免旧cycle单消费者成为全账户瓶颈；单页预算25秒，超时保留游标并释放running。
- Stream消费错误后自动退避重连。补齐已投递通知丢失、任务仍idle的恢复，只恢复频道真正队首。真实PG回归已验证修复前失败、修复后通过。
