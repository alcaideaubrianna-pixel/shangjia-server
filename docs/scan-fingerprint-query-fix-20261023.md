# 扫图超时修复与本地验证

基线 `32026aa3`。本次只修改扫图精确/批量近似查询及回归测试，不启动发布 Worker，不向 Telegram 发送消息，不执行线上迁移。

## 已确认的原因

1. 原 MD5 索引以 `account_id` 开头。事件用户有 503 个可见账户，单次查询即使没有命中也会执行大量账户探测；线上只读计划中耗时约 1.45 秒。
2. pHash 批量查询把大量距离不合格的桶记录先物化，之后才计算完整距离。实际计划出现约 31.9 万、64.5 万条中间记录，最终只有几十条候选，消耗了精确和近似共享的 5 秒预算。
3. 先前的小规模临时表、均匀随机数据及缓存命中测试，不能覆盖大权限范围和热点桶，也不能代替真实规模的首次查询验证。

## 修改

- 增加 MD5 开头的部分覆盖索引，精确查询先按指纹获取候选，再校验租户、账户、资料和归属有效性。继续保留旧账户索引；MD5 优先级不变。
- pHash 在各索引分支中提前排除不可能命中任何输入的完整指纹，再物化桶记录。预过滤使用参数化常量输入表达式，避免每条索引记录都重新扫描输入 CTE。未增加候选截断，保留每个输入原有桶命中数、距离、有效性校验和排序。
- 完全失败的候选查询在提前返回前标记 `SearchProgress.Incomplete`，不把未完成查询当成完整空结果。
- 补齐上传回退测试的有效媒体归属，避免用不存在的媒体 ID 测试了错误分支。

- 热点桶：一半干扰媒体与原故障输入共享一个 16 位桶；四组真实输入逐张比较原查询结果、桶命中数、删除和归属约束，通过。ICFBUMHJ 批量 SQL 本次约 0.29～0.38 秒，仅为本地合成规模结果。
- 阈值 0/12/14/15、桶探测/小范围扫描、别名、跨租户/账户隔离、资料/归属删除、缺失收录记录、重复输入均有 PostgreSQL 执行验证。
- 原事件 40 组、156 张输入身份检索回放通过：22 张身份命中、134 张仍需指纹查询。这不是完整扫图耗时。

- 搜索单元测试竞态检测通过；`utility/scantrace` 全部测试和竞态检测通过。
- 完整 Publish/Bot 包回归仍有 6 个既有顶层失败：防扫图并发默认值、旧重复扫描桶数量断言、消息分类、资料标识解析、两个中转帮助文案测试。已用基线源码 overlay 复测，相同失败。本次不修改这些无关生产行为，不能宣称全仓库测试通过。

真实指纹快照回放使用 `TestScanOfflineCorpusReplay`，固定独立数据库 `youban_scan_offline_20261023`。测量精确→近似→候选合并流程，应用缓存每轮清空；不包含下载/哈希、最终资料详情加载、Telegram 回复耗时，不等于完整用户端 3 秒承诺。

## 部署前置条件（本轮未执行）

先在事务外单独执行 `server/addons/youban_publish/resource/sql/scan_fingerprint_lookup.pgsql.sql`。使用 `CREATE INDEX CONCURRENTLY`，不阻断正常写入，但索引构建仍会增加 I/O/CPU，应观察数据库负载。禁止将其放进事务或每次请求的初始化逻辑。

执行后检查实际索引定义和有效性；只有 `indisvalid=true` 且定义匹配才部署代码。`IF NOT EXISTS` 不会修复同名无效索引，若前次构建失败，应单独处理并重新验证，不能仅凭 SQL 返回成功继续发布。

```sql
SELECT i.indisvalid,i.indisready,pg_get_indexdef(i.indexrelid)
FROM pg_index i
WHERE i.indexrelid=to_regclass('public.idx_ybp_media_md5_lookup');
```

回滚代码可继续保留新索引，旧查询仍可工作；不必在回滚时删除索引。新增索引增加存储和媒体写入成本，部署后需要检查实际命中计划、首次搜索耗时及查询取消率。
