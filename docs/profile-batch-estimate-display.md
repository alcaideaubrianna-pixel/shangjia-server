# 资料详情的批次循环排位说明

展示格式为：

> 预计 3 天后轮到 · 前方 210 份 · 每天 70 份

批次循环使用频道内的连续轮播顺序，每天选择最多配置数量的不同资料。
“3 天”只是文案示例，不是把所有资料的等待时间改成 3 天。
本文描述新实现；代码上线前必须完成轮播索引和每日快照的显式数据库迁移及历史回填。

## 连续轮播规则

- 只以资料当前已上架、公开且未删除作为资料生命周期资格；保留频道、租户和账户的访问边界。
- 不按资料创建时间、历史成功任务是否存在、任务显示状态或媒体就绪状态排除候选。
- 每个频道独立保存轮播顺序。首次入选登记成员；发送成功后移动至队尾，同一成功任务重复投影不重复移动。
- 每日保存有限、持久化的候选快照，按快照序号分页。发送过程中队列顺序变化不改变当天名单。
- 每天最多选择配置数量的不同资料；不足该数量时只选实际数量，同一天不通过重复资料补量。
- 发送失败、媒体等待及复用已有任务交给发送链路处理，不将创建任务数解释为成功资料数。

例如 263 份资料、每天 70 份：

| 发送日 | 当天名单 |
|---|---|
| 第 1 天 | 原队首 1～70 |
| 第 2 天 | 原队首 71～140 |
| 第 3 天 | 原队首 141～210 |
| 第 4 天 | 原队首 211～263，加上已轮回队尾的 1～17 |

上述例子假定每天全部发送成功、没有新增或下架，实际间隔通常是 3 或 4 个发送日。
新增资料首次发布成功后进入队尾，不再额外等待“本轮剩余 + 下一轮创建时间前缀”。

## 接口

`profile/channels` 及详情的 `pushChannels` 使用同一个 `ProfilePushChannelModel`。
保留 `nextPushAt`、`nextPushAtEstimated`、`cycleBatchSize`，新增：

| 字段 | 含义 |
|---|---|
| `batchAheadCount` | 预计轮到之前的有效资料数量，不是已入队的任务数量 |
| `batchRoundRemaining` | 旧固定轮次字段，连续轮播不再据此计算日期 |
| `batchWaitingNextRound` | 旧固定轮次字段，连续轮播不再设置为等待下一轮 |
| `batchInCurrentRun` | 资料是否属于尚待执行的当前每日快照；不代表正在发送 Telegram 消息 |

两个数量字段使用可选整数。缺失表示无法预估，`0` 表示已知为零。
查询超时、目标不满足资格、批次大小无效、未启用批次循环时不伪造数量。
旧前端会忽略新字段；新前端收到旧接口时保留日期或等待排期提示。

## 排期与性能边界

预估与调度必须使用同一个频道轮播索引及上架资格，不得重新按创建时间或资料 ID 排位。
当前批次成员通过持久化快照核对，不再用“排名小于批次数量”猜测。
尚未执行的当前快照与未来每日额度分别计算；已经发送并回到队尾的成员不能再次扣除。
日期使用北京时间，排位会随新增、上下架、发送结果及频道配置变化，不是发送承诺。

候选查询从带频道前缀的轮播索引开始，再通过资料主键核对上架状态；
快照通过 `(run_id, ordinal)` 分页，不用 OFFSET 或创建时间游标。
预估仅允许频道范围的索引查询并缓存，不能扫描整张资料表、历史任务表或 Redis 全部 key。
旧 `cycle_batch_cursor` / `cycle_round_end_id` 不能当成新的轮播进度继续使用。

此前 F50025 的“前方 507 份、7 天”来自旧规则中的
`当前轮剩余 247 + 下一轮前缀 260`，是待替换的旧算法结果。
新版本应按迁移后的真实轮播位置重新计算，不能硬编码改成 3 天或 4 天。
