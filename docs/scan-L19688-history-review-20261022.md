## 统计口径

Telegram 用户 ID 8213866140，Bot 1，绑定账号 7、租户 6。SLS 查询时间范围为 2026-10-01 08:00 至 2026-10-23 08:00（北京时间）。实际匹配的入口日志从 10 月 14 日开始，按分页取全 436 条相关日志，得到 97 个媒体组追踪号。它不是所有历史扫图请求总量：旧版单图和入口缺日志的请求无法据此完整统计。

- 其中 19 个最终搜索返回超时错误；另 9 个最终搜索没有返回错误，不等于整个回复链路没有失败。
- 还发现 10 月 14 日两次 text is too long；这是回复失败，不计为超时。
- 40A80308 仍未出现在本次查询中。今天 17:15 的实际日志追踪号是 YOEKMFUD，不能仅凭用户和时间把两个编号视为同一次请求。

## 本地结果及边界

新增 TestScanIncidentIdentityLocalReplay，连接固定的本机 PostgreSQL 127.0.0.1:35432，使用事务临时表和 DBX 导出的真实发送记录；覆盖已失去资料状态关联和范围外记录的排除、全部入站图片尺寸及转发身份匹配。测试不启动 Worker，不发送 Telegram 消息。

- 40 批 / 156 条输入通过；普通模式最慢身份查询 9.14 ms，race 模式最慢 69.64 ms。
- 仅 22 条媒体直接命中发送记录；其余 134 条仍需指纹路径，不代表没有搜索结果。
- 这些毫秒数据只属于本地身份匹配，不是整个搜索、下载或回复耗时；本地临时表也不等于生产数据规模。
- 通过新代码原有 SQL 生成函数导出真实指纹的 LSH/范围扫描 SQL，供 DBX 复查。
- 对 ICFBUMHJ 第一张图片执行只读 EXPLAIN ANALYZE（LSH 策略），返回 4 条候选，执行计划的 Shared I/O Read Time 为 2924.214 ms。这是实测磁盘读取耗时，不是网络时间，也不是完整请求时间；足以证明冷读时无法仅凭免下载优化保证完整链路 3 秒。该单条探测没有设置运行时的 jit/work_mem 参数，不能当作完整运行时复测。
- 另一次尝试以只读事务设置与运行时相同参数并限制 3 秒的 DBX batch 返回 COMMIT failed: connection closed，未获取可用执行结果，不计入成功复测，也不能据此断言实际 SQL 超时。

YOEKMFUD 的历史搜索本身完成，但结果相册发送遇到 Wrong file identifier/HTTP URL specified，随后 result.media.fallback_prepare / result.media / result.view 超时约 19 秒。这是回复媒体链路的问题，身份搜索优化不会自动修复它。

结论：新代码的身份命中路径已通过上述本地真实输入回归，但尚不能声称这批历史问题全部解决。还需要针对大范围相似查询的冷读、无效回复 file_id 的降级准备进行独立修复及完整链路验证。
