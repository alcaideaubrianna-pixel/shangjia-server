# 同频道多采集源的规则归属

## 故障与修复

频道 `3954550954` 在租户 87、账户 628 下同时配置来源 457、487，
分别绑定规则 449、476。入口已经按来源分发 Bot 更新，但旧规则解析又按
“租户＋账户＋频道”重选来源，查到两条后直接报错；旧路由缓存也没有入口来源维度。

规则解析现在直接使用事件的 source_id，删除频道重选来源函数及其缓存读写，
并移除保存采集源时“同频道只能有一个启用来源”的检查。规则缓存切换为 v2，
继续按 tenant/account/source 隔离，不读取旧规则结果。

同频道多来源是合法配置。各来源的规则、后缀、目标频道独立；
没有自身规则或自身规则被禁用时不能回退到其他来源。来源开关和频道人工禁用
仍由原有入口、processCollectEvent 和频道关系检查控制。本次没有修改这些开关。

## 验证

本地专项测试使用独立 Docker PostgreSQL，未接入生产库或启动业务消费者。
测试实际调用 collectEventRules，覆盖：

- 457、487 同时启用，分别得到自己的规则、后缀及目标频道。
- 短 Chat ID 与 `-100` Chat ID、交替调用和缓存命中时不串来源。
- 残留旧路由缓存、旧版本规则缓存不影响新路径。
- 其他租户和账户的规则不能混入。
- 本来源的规则或绑定被禁用后报错，不借用另一个来源继续执行。
- 缺少 source_id 时在读取缓存和数据库前报错。

专项测试通过；测试编译使用 `GOMAXPROCS=2`、`GOMEMLIMIT=2GiB`、`-p 1`，
对较大的 sys 包关闭内联以减少本地编译开销。
受限并发 `go build -p 1 ./...` 和架构 guard 自测通过。
全仓 guard 扫描仍报告既有 tg_media_fallback_handoff.go 和
tg_video_sanitize_cache.go 问题，本次未修改这些文件、检查器或 baseline。

## 上线与历史恢复

本修复不需要 SQL 结构迁移、来源合并、来源删除或批量清理 Redis。
旧缓存由新路径忽略，自行过期。保存配置的 web 与实际调用 processCollectEvent
的消费者都需要更新，不能只更新前端或 API。

已有 pending/重试任务是否继续处理需部署后按 eventId 验收；
已经到达失败终态或被人工禁用的事件不能视为自动恢复，需按 source_id
生成有界的运维修复预览，再通过已有重放接口处理。不得重新启用用户禁用的来源，
也不得把历史任务的来源改成另一条来源。

本轮未部署、未重放生产任务、未改变生产配置；本地通过不代表线上已恢复。
