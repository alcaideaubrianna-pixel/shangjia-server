# 采集处理与媒体缓存队列阻塞事故复盘

日期：2026-10-08

## 摘要

用户侧表现为采集任务长时间停留在“待处理/待缓存”，多个租户的资料不能及时进入媒体缓存和后续上架流程。本次不是单点故障，而是三个已经确认的故障连续叠加：采集处理任务重复放大造成跨租户饥饿；媒体 Worker 无法访问错误配置的 Telegram Bot API 宿主机地址；媒体队列重排工具又受到残留 Asynq Unique 锁影响，导致数据库事件与队列任务脱节。

## 影响

- 故障排查时数据库有 14,512 个未完成采集事件，但只有 125 个有效处理分区。
- Asynq 采集处理队列一度约有 6,500 个任务，绝大部分是同一分区的重复唤醒。
- 热点 `source_id=78` 约有 13,000 个未处理事件，挤占共享队列，其他租户出现饥饿。
- `source_id=324` 的 80 条历史采集事件被阻塞；进入媒体阶段后又因 Bot API 连接超时而无法形成有效吞吐。

## 时间线与根因链

1. 采集调度标记 TTL 为 30 至 35 分钟；队列等待超过 TTL 后，同一个 `tenant_id + account_id + source_id + source_chat_id` 被再次投递。
2. 重复任务持续进入单一共享队列，任务数远高于实际有效分区数，热点来源导致其他租户饥饿。
3. 媒体 Worker 使用数据库中的 `http://10.3.4.11:18081` 和 `http://10.3.4.11:18083`。Worker 与 Bot API 同在 `dokploy-network`，但容器访问宿主机发布端口发生连接超时；每次失败约占用 2 分 15 秒。
4. 运维执行媒体队列重排。命令删除等待任务后立即重建，但正常投递带有 `asynq.Unique(24h)`；删除任务不会删除 Unique 锁，重建被 `ErrDuplicateTask` 跳过。
5. 最终出现 `media_pending` 仍存在、Asynq 队列中却没有对应任务的状态，自动处理无法继续。

根因链如下：

```text
调度标记 TTL 过期
-> 同一处理分区重复入队
-> 热点来源占满共享队列并造成跨租户饥饿
-> 事件进入媒体阶段后 Bot API 宿主机地址连接超时
-> 媒体吞吐接近停滞
-> 重排时残留 Unique 锁阻止任务重建
-> 数据库 media_pending 与 Asynq 任务脱节
```

## 为什么没有提前告警

- 原监控只观察队列总长度，没有比较“队列任务数”和“有效数据库分区数”，无法识别重复放大。
- Worker 心跳只能证明进程存活，不能证明正在产生吞吐。
- Bot API 已有请求和耗时指标，但没有对应错误率、网络错误和高延迟告警。
- 没有检查超时 `media_pending` 是否存在对应的 pending/active/scheduled/retry Asynq 任务。
- 重排命令只输出删除和重建数量，没有把有效数据库事件、活动任务和重建结果作为必须满足的不变量。

## 已完成修复

- `f06b0f72`：采集处理按租户账号分片到 16 个公平队列；已有调度标记命中时续期；任务完成前二次检查，防止并发丢唤醒；保留旧队列消费以支持平滑升级。
- 生产配置改为 Docker 服务 DNS：Bot API `http://xiaohuiji-telegram-bot-api-ezbfcz:8081`，文件服务 `http://xiaohuiji-telegram-bot-files-y1qn4q`。
- `1c90974b`：媒体重排重建时绕过残留 Unique 锁，正常实时投递仍保留 24 小时去重。
- 增加采集处理放大比、超时媒体事件、媒体事件缺少 Asynq 任务、监控自身健康指标。
- 增加 Bot API getFile 错误、P95 延迟、文件下载网络错误告警。

## 后续规避措施

1. 采集处理任务数超过有效分区数 3 倍持续 5 分钟告警，超过 10 倍持续 2 分钟升级为 CRIT。
2. 任一 `media_pending` 超过 10 分钟告警；超时事件没有对应 Asynq 任务时单独触发 CRIT。
3. 本地 Bot API 5 分钟错误超过 5 次或 getFile P95 超过 5 秒时告警。
4. 所有队列运维命令增加闭环校验：`活动任务 + 重建任务 + 明确跳过任务` 必须覆盖有效数据库分区或事件；不满足时命令返回错误。
5. 生产启动配置校验禁止 Bot API 使用宿主机私网 IP，容器部署统一使用 Docker 服务 DNS。
6. 每次队列分片、去重 TTL 或重排逻辑变更必须包含以下故障注入测试：队列等待超过 TTL、删除任务但保留 Unique 锁、Bot API 连接超时、单租户热点积压。

## 验证标准

- 正常状态下采集处理队列放大比接近 1，不应持续超过 3。
- `media_pending_stale_events` 和 `media_pending_missing_asynq_task` 均为 0。
- 有待处理事件时，处理计数持续增长；Worker 心跳不能单独作为健康结论。
- 队列重排完成后必须报告并核对数据库有效任务数、活动数、删除数、重建数和跳过数。
